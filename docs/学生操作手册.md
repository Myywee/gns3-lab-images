# GNS3 网络实验学生操作手册

> 适用实验：实验一、实验二、实验三、实验四、实验六。实验五不在本手册范围内。

> 本手册已经拆分为独立实验分册。新使用者请从[分册目录](学生操作手册/README.md)进入；本文件继续保留为汇总版，避免已有链接失效。

## 1. 手册使用说明

本课程使用发布在 `ghcr.io/myywee` 的预制 Docker 镜像。实验一、二、三各有两个阶段：

- `start`：学生开始实验时使用的基线环境；
- `complete`：完成态检查点，用于结果核验、故障恢复或教师演示。

正常实验应从 `start` 工程开始，在当前容器的可写层中完成配置和验证。不要一开始就使用 `complete` 代替实验操作。需要与标准完成态比较，或基线环境已经无法恢复时，再按教师要求打开 `complete` 工程。

实验四和实验六只有 `complete` 镜像；镜像只负责提供工具和实验程序，抓包、故障注入、数据记录与分析仍由学生完成。

所有安全实验只能在课程提供的隔离 GNS3 环境中进行。不得把 XSS、CSRF、口令测试或扫描操作用于未授权系统。

镜像均为公开镜像，正常情况下不需要登录。若网络提示超时，先检查 GNS3 VM 的 DNS、代理和互联网连接，不要改用不明来源的同名镜像。

### 3.2 创建 GNS3 Docker 模板

对上表中的每个镜像创建独立模板：

1. 打开 **Edit → Preferences → Docker containers → New**；
2. 选择运行 Docker 的 GNS3 Server/GNS3 VM；
3. 选择已有镜像并使用可识别的模板名，例如 `lab1-start-web`；
4. 网卡数量设为 `1`，Console 类型设为 `Telnet`；
5. 保持容器以 root 身份运行；
6. 按下文为节点填写 **Start command**；
7. 实验二、三的 Web-Server 还需按第 3.5 节准备证书挂载。

不要通过修改一个公用模板来切换阶段，否则其他工程中的同模板节点也可能受影响。建议每个阶段创建单独模板和单独 GNS3 工程副本。

### 3.3 实验一至三的拓扑和地址

```text
GNS3 NAT
└── Core-Router G0/3（DHCP，NAT outside）
    ├── G0/0  10.10.20.1/24 ── SW-SERVER
    │                            ├── DNS-Server 10.10.20.10/24
    │                            └── Web-Server 10.10.20.20/24
    ├── G0/1  10.10.10.1/24 ── SW-MGMT
    │                            └── Administrator 10.10.10.10/24
    └── G0/2  10.10.30.1/24 ── SW-CLIENT
                                 ├── Client1 10.10.30.10/24
                                 └── Client2 10.10.30.20/24
```

路由器首次配置：

```text
enable
configure terminal
hostname Core-Router
no ip domain-lookup

interface GigabitEthernet0/0
 description SERVER-NETWORK
 ip address 10.10.20.1 255.255.255.0
 ip nat inside
 no shutdown
 exit

interface GigabitEthernet0/1
 description MANAGEMENT-NETWORK
 ip address 10.10.10.1 255.255.255.0
 ip nat inside
 no shutdown
 exit

interface GigabitEthernet0/2
 description CLIENT-NETWORK
 ip address 10.10.30.1 255.255.255.0
 ip nat inside
 no shutdown
 exit

interface GigabitEthernet0/3
 description GNS3-NAT-WAN
 ip address dhcp
 ip nat outside
 no shutdown
 exit

ip access-list standard NAT_INSIDE
 permit 10.10.10.0 0.0.0.255
 permit 10.10.20.0 0.0.0.255
 permit 10.10.30.0 0.0.0.255
 exit

ip nat inside source list NAT_INSIDE interface GigabitEthernet0/3 overload
ip route 0.0.0.0 0.0.0.0 dhcp
end
write memory
```

如果实际接口编号不同，以 `show ip interface brief` 和 GNS3 链路标签为准，只替换接口名，不改变地址规划。

### 3.4 实验一至三的 Start command

Client 镜像自带入口脚本：`lab1-complete` 会启动本地 dnsmasq 并把解析器指向 `127.0.0.1`；`lab1-no-cache` 会把解析器直接指向 `10.10.20.10`。因此 Client 的 Start command 只配置接口和默认路由，不要再次覆盖 `/etc/resolv.conf`。


Client2：

```text
/bin/bash -lc '/gns3/bin/busybox ip link set eth0 up; /gns3/bin/busybox ip addr flush dev eth0; /gns3/bin/busybox ip addr add 10.10.30.20/24 dev eth0; /gns3/bin/busybox ip route replace default via 10.10.30.1 dev eth0; exec /bin/bash'
```

Administrator：

```text
/bin/bash -lc '/gns3/bin/busybox ip link set eth0 up; /gns3/bin/busybox ip addr flush dev eth0; /gns3/bin/busybox ip addr add 10.10.10.10/24 dev eth0; /gns3/bin/busybox ip route replace default via 10.10.10.1 dev eth0; exec /bin/bash'
```

DNS-Server：

## 4. 实验一：Web 服务器与 DNS 基础

### 4.1 实验目标

1. 验证三个内网网段的路由和 PAT；
2. 观察 HTTP 请求、响应和状态码；
3. 发现并修复 `/secure/` 与 `/.git/` 的未授权访问；
4. 区分权威 DNS、递归解析和客户端缓存；
5. 观察“客户端缓存 → 本地 BIND → 根/TLD/权威 DNS”的查询路径。

### 4.2 启动 `lab1-start`

启动 Router、NAT、三台客户端、DNS-Server 和 Web-Server。先验证地址、路由和端口：

```bash
ping -c 2 10.10.20.10
ping -c 2 10.10.20.20
ping -c 2 1.1.1.1
```

DNS-Server：

```bash
ss -lnutp | grep ':53'
dig @10.10.20.10 www.experiment.test A +short
```

Web-Server：

```bash
ss -lntp | grep ':80'
nginx -t
```

`www.experiment.test` 应解析为 `10.10.20.20`。

### 4.3 任务一：发现 Web 访问控制问题

在 Client1 执行：

```bash
curl -s -o /dev/null -w '/ = %{http_code}\n' http://10.10.20.20/
curl -s -o /dev/null -w '/secure/ = %{http_code}\n' http://10.10.20.20/secure/
curl -s -o /dev/null -w '/.git/HEAD = %{http_code}\n' http://10.10.20.20/.git/HEAD
curl -s -o /dev/null -w '/.git/config = %{http_code}\n' http://10.10.20.20/.git/config
```

`lab1-start` 中四个请求均可返回 `200`。检查 Web-Server 的 `/etc/nginx/sites-available/default`，说明为什么 `location /` 没有保护内部目录和隐藏文件。随后在 start 环境中补充：

```nginx
location ^~ /secure/ {
    deny all;
}

location ~ /\. {
    deny all;
    access_log off;
    log_not_found off;
}
```

检查并重新加载：

```bash
nginx -t
nginx -s reload
```

重新执行四个请求，预期 `/` 为 `200`，其余敏感路径为 `403`。

### 4.4 任务二：从关闭递归切换到受限递归

初始镜像只对 `experiment.test` 提供权威回答，不提供公网递归。在 Client1 执行：

```bash
dig @10.10.20.10 www.experiment.test A +noall +comments +answer
dig @10.10.20.10 www.example.com A +noall +comments +answer
```

第一个查询应返回 `10.10.20.20`；第二个查询不应得到公网 A 记录，响应不应包含 `ra`。

在 DNS-Server 备份并编辑 `/etc/bind/named.conf.options`，把关键项改为：

```text
allow-query { lab_networks; };
allow-recursion { lab_networks; };
allow-query-cache { lab_networks; };
recursion yes;
```

不要添加公共 DNS `forwarders`，否则不能观察 BIND 自己查询根、TLD 和权威服务器的过程。检查并重启：

```bash
named-checkconf
rndc stop 2>/dev/null || pkill -TERM named
while pgrep -x named >/dev/null; do sleep 1; done
/usr/sbin/named -u bind -c /etc/bind/named.conf
```

如果当前控制台被前台 `named` 占用，可停止节点并把修改保存在项目持久目录后重启，或另开 Console。再次查询 `www.example.com`，预期状态为 `NOERROR`，响应包含 `rd ra` 和公网地址。

### 4.5 任务三：比较 Client1 与 Client2 的缓存路径

在 `lab1-start` 中两台客户端均无本地缓存。完成态中只有 Client1 使用本地 dnsmasq，Client2 和 Administrator 仍直连 BIND。

打开 `lab1-complete` 后，在 Client1 执行：

```bash
cat /etc/resolv.conf
ss -lnup | grep '127.0.0.1:53'
: > /var/log/dnsmasq-lab.log
kill -HUP "$(cat /run/dnsmasq-lab.pid)"
dig www.example.com A +noall +answer +stats
dig www.example.com A +noall +answer +stats
grep -E 'forwarded|cached|reply' /var/log/dnsmasq-lab.log
```

预期解析器为 `127.0.0.1`，第一次查询出现 `forwarded ... to 10.10.20.10`，第二次出现 `cached`。

在 Client2 执行：

```bash
cat /etc/resolv.conf
dig www.example.com A +noall +answer +stats
```

Client2 的解析器应直接为 `10.10.20.10`。

### 4.6 抓包与提交内容

建议同时抓取 Client1—SW-CLIENT、DNS-Server—SW-SERVER、Router—NAT 和 Web-Server—SW-SERVER 链路。常用过滤器：

```text
dns
dns.flags.response == 0 && ip.src == 10.10.20.10
http || tcp.port == 80
```

提交内容：

- 路由器接口、默认路由和 NAT 转换截图；
- Web 漏洞修复前后的四个 HTTP 状态码；
- 关闭递归和启用递归后的 `dig` 对比；
- BIND 首次迭代查询及第二次缓存命中的抓包证据；
- Client1 本地缓存与 Client2 直连 BIND 的对照证据。

## 5. 实验二：复杂 Web 部署与 HTTPS

### 5.1 实验目标

1. 验证静态资源的缓存策略和跨源资源共享；
2. 观察本地 DNS 覆盖前后，同一域名指向不同站点的变化；
3. 检查证书链、私钥匹配关系和主机名；
4. 配置并验证 HTTPS 与 HTTP 301 跳转；
5. 用抓包区分明文 HTTP、TLS 握手和加密后的应用数据。

### 5.2 启动 `lab2-start`

确认 Web 服务和 DNS 递归服务已启动：

```bash
dig @10.10.20.10 networking-experiments.nju-slab.cn A +short
curl -I http://10.10.20.20/
```

`lab2-start` 的 DNS-Server 尚未为课程域名建立本地区域，因此对该名称的查询会通过公网递归得到公网结果；Web-Server 已在 `10.10.20.20:80` 提供实验主页。

使用指定地址访问本地站点：

```bash
curl --resolve networking-experiments.nju-slab.cn:80:10.10.20.20 \
  -I http://networking-experiments.nju-slab.cn/
```

### 5.3 任务一：检查缓存策略和 CORS

先从首页找出一个 CSS/JS、图片或字体以及 HTML 路径，再分别检查响应头：

```bash
curl --resolve networking-experiments.nju-slab.cn:80:10.10.20.20 \
  -I http://networking-experiments.nju-slab.cn/

curl --resolve networking-experiments.nju-slab.cn:80:10.10.20.20 \
  -I http://networking-experiments.nju-slab.cn/实际静态资源路径
```

记录并解释：

| 资源类型 | 预期 `Cache-Control` | 其他预期头部 |
|---|---|---|
| HTML | `no-store, no-cache, must-revalidate` | — |
| CSS/JS | `public, max-age=7200` | — |
| 图片/字体 | `public, max-age=2592000` | `Access-Control-Allow-Origin: *` |
| PDF | `public, max-age=86400` | — |

隐藏文件路径应返回 `403`。把请求与响应头保存为实验报告证据。

### 5.4 任务二：建立本地 DNS 覆盖

在 DNS-Server 中新增区域 `networking-experiments.nju-slab.cn`，区域顶点和 Web 地址均指向 `10.10.20.20`。完成后必须通过：

在 `/etc/bind/named.conf.local` 末尾加入：

```text
zone "networking-experiments.nju-slab.cn" {
    type master;
    file "/etc/bind/db.networking-experiments.nju-slab.cn";
};
```

创建 `/etc/bind/db.networking-experiments.nju-slab.cn`：

```text
$TTL 300
@       IN      SOA     ns.networking-experiments.nju-slab.cn. admin.networking-experiments.nju-slab.cn. (
                        2026090901 ; Serial
                        3600       ; Refresh
                        900        ; Retry
                        604800     ; Expire
                        300 )      ; Negative Cache TTL

@       IN      NS      ns.networking-experiments.nju-slab.cn.
@       IN      A       10.10.20.20
ns      IN      A       10.10.20.10
```

设置权限后检查并加载：

```bash
chown root:bind /etc/bind/db.networking-experiments.nju-slab.cn
chmod 640 /etc/bind/db.networking-experiments.nju-slab.cn
named-checkconf
named-checkzone networking-experiments.nju-slab.cn \
  /etc/bind/db.networking-experiments.nju-slab.cn
rndc reload
```

在 Client1 清空本地 dnsmasq 缓存后验证：

```bash
kill -HUP "$(cat /run/dnsmasq-lab.pid)"
dig networking-experiments.nju-slab.cn A +short
curl -I http://networking-experiments.nju-slab.cn/
```

预期域名由公网地址切换为 `10.10.20.20`。抓包中不应再出现为该名称发往公网 DNS 的查询，因为本地 BIND 已成为该区域的权威服务器。

### 5.5 任务三：证书核验

在 Web-Server 只读取证书元数据，不显示私钥内容：

```bash
openssl x509 -in /etc/nginx/certs/networking-experiments.nju-slab.cn.fullchain.pem \
  -noout -subject -issuer -dates -ext subjectAltName

openssl x509 -in /etc/nginx/certs/networking-experiments.nju-slab.cn.fullchain.pem \
  -pubkey -noout | openssl pkey -pubin -outform der | sha256sum

openssl pkey -in /etc/nginx/certs/networking-experiments.nju-slab.cn.key \
```

complete 阶段应具备以下变化：

- 反射型和存储型输出均被 HTML 转义；
- session Cookie 使用 `Secure; HttpOnly; SameSite=Lax`；
- `/profile` 包含 64 个十六进制字符的 CSRF Token；
- 无 Token、错误 Token和已经使用过的旧 Token均返回 `403`；

重新提交第 6.3 节的反射型和存储型测试字符串：危险字符应作为普通文本显示，不能再作为脚本执行。只有终端时，检查响应中的 `<`、`>` 是否被编码为 `&lt;`、`&gt;`。再次执行第 6.4 节的 `Set-Cookie` 检查，确认同时出现 `Secure`、`HttpOnly` 和 `SameSite=Lax`。

`SameSite` 描述的是“站点”边界，不等同于“同源”。本实验两个主机名同属 `nju-slab.cn`，所以不能把 `SameSite=Lax` 当作这里唯一的 CSRF 防线；服务端 CSRF Token 才是无 Token 请求被拒绝的关键。curl 也不会自动实施浏览器的 SameSite 策略。

登录并提取 Token：

```bash
rm -f /tmp/lab3-cookies.txt /tmp/lab3-profile.html

curl -sS -c /tmp/lab3-cookies.txt -o /dev/null \
  -w 'login-http=%{http_code}\n' \
  -d 'username=admin&password=admin123' \
  https://networking-experiments.nju-slab.cn/login

curl -sS -b /tmp/lab3-cookies.txt -o /tmp/lab3-profile.html \
  https://networking-experiments.nju-slab.cn/profile

csrf_token=$(sed -n \
  's/.*name="csrf_token" value="\([a-f0-9]*\)".*/\1/p' \
  /tmp/lab3-profile.html | head -n 1)
printf 'token-length=%s\n' "${#csrf_token}"
```

预期长度为 `64`。先验证无 Token 被拒绝：

```bash
curl -sS -b /tmp/lab3-cookies.txt \
  -H 'Origin: https://networking-experiments-2.nju-slab.cn' \
  --data 'new_password=bad' \
  -o /tmp/lab3-without-token.txt \
  -w 'without-token=%{http_code}\n' \
  https://networking-experiments.nju-slab.cn/change-password
cat /tmp/lab3-without-token.txt
```

再验证正确 Token 能改密：

```bash
curl -sS -b /tmp/lab3-cookies.txt -c /tmp/lab3-cookies.txt \
  -H 'Origin: https://networking-experiments.nju-slab.cn' \
  -H 'Referer: https://networking-experiments.nju-slab.cn/profile' \
  --data-urlencode 'new_password=good' \
  --data-urlencode "csrf_token=$csrf_token" \
  -o /tmp/lab3-with-token.txt \
  -w 'with-token=%{http_code}\n' \
  https://networking-experiments.nju-slab.cn/change-password
cat /tmp/lab3-with-token.txt
```

最后携带更新后的 Cookie 重放旧 Token，预期返回 `403`：

```bash
curl -sS -b /tmp/lab3-cookies.txt \
  --data-urlencode 'new_password=reused' \
  --data-urlencode "csrf_token=$csrf_token" \
  -o /tmp/lab3-replay-token.txt \
  -w 'replay-old-token=%{http_code}\n' \
  https://networking-experiments.nju-slab.cn/change-password
cat /tmp/lab3-replay-token.txt
```

清理所有 Cookie、Token 和响应临时文件。报告中只记录长度、状态码和是否轮换，不记录具体 Cookie 或 Token 值。

```text

<算法>_<轮次>_iperf.json
<算法>_<轮次>_ss.log
<算法>_<轮次>_events.log
```

## 8. 实验六：TCP 与 UDP Socket Echo

实验六复用实验四的三节点拓扑、地址和链路参数，替换 Client/Server 镜像即可。正常阶段丢包率为 `0%`，丢包实验阶段为 `5%`。

### 8.1 启动 TCP 与 UDP Echo Server

在 Server 执行：

```bash

```

预期同时出现 TCP `LISTEN` 和 UDP `UNCONN`。TCP 和 UDP 端口空间独立，因此可以同时绑定端口 18080。

### 8.2 无丢包基线

```bash

```

过滤器：

```text
tcp.port == 18080 || udp.port == 18080
```

记录 TCP 三次握手、Echo、四次挥手；对比 UDP 第一个数据报之前没有握手。保存为 `exp6_baseline.pcapng`。

### 8.3 监听 Socket、连接 Socket和四元组

Client 发起较大传输：

```bash

  --server 10.20.20.20 --port 18080 \
  --size 8388608 --timeout 20
```

传输期间在 Server 执行：

```bash

ss -tnp 'sport = :18080'
```

记录监听 Socket 的本地端点，以及至少一条 `ESTAB` 连接的源 IP、源端口、目的 IP、目的端口。说明为什么多个连接能共用服务器的 TCP/18080。

### 8.4 显式源端口与并发连接

Client：

```bash

  --source-ip 10.10.10.10 --source-port 20001 \
  --msg 'tcp fixed source port'

  --source-ip 10.10.10.10 --source-port 20002 \

```

在抓包中确认源端口分别为 20001、20002。随后可用 20011、20012、20013 启动三个后台 TCP Client，并在 Server 通过 `ss -tnp 'sport = :18080'` 观察并发四元组。

### 8.5 随机丢包：TCP 恢复与 UDP 超时

把 R1—Server 链路 Packet loss 改为 `5%`。

TCP：

```bash
timeout 120s python3 tcp_echo_client.py \
  --server 10.20.20.20 --port 18080 \
  --size 1048576 --timeout 30
```

UDP：

```bash
python3 udp_echo_client.py \
  --server 10.20.20.20 --port 18080 \
  --count 50 --size 1200 --interval 0.05 --timeout 0.5
```

每种协议至少重复 5 轮。TCP 应出现重传并最终收到完整 Echo；UDP 可能出现序号超时且不会自动补发。应用观察到的 UDP 超时率不要求严格等于 5%，因为请求和响应两个方向均可能丢包。分别保存 `exp6_loss_tcp.pcapng` 与 `exp6_loss_udp.pcapng`，完成后立即把丢包率恢复为 `0%`。


| 现象 | 优先检查 |
|---|---|
| 节点启动后没有地址 | Start command、接口名是否为 `eth0`、模板是否使用正确镜像 |
| 跨网段不通 | Router 接口是否 `up/up`、默认网关和掩码是否正确 |
| 公网 IP 不通 | Router 默认路由、inside/outside、NAT ACL 和 GNS3 NAT |
| DNS 内部域名失败 | `named` 进程、TCP/UDP 53、区域文件、`named-checkconf -z` |
| Client1 DNS 失败 | dnsmasq 是否监听 `127.0.0.1:53`、上游是否为 `10.10.20.10` |
| Web 端口未监听 | Start command 是否调用对应启动脚本，查看 nginx/Flask 日志 |
| HTTPS 启动失败 | 只读挂载、文件名、私钥权限、证书与私钥是否匹配 |
| lab3 两域名只有一个可用 | DNS 是否为 `lab3-complete`，证书 SAN 是否覆盖两个名称 |
| BBR 不可用 | 在 GNS3 Docker 宿主内核启用；不要在容器内加载模块 |
| GNS3 丢包设置无效果 | 修改的是否为 R1—Server 正确链路，是否点击 Apply |
| 结果文件消失 | Docker 可写层随节点重建丢失；每轮结束立即导出证据 |

## 10. 实验报告通用要求

每份报告至少包含：

1. 实验阶段、节点镜像标签和拓扑截图；
